Daily Options Watchlist Mirror

Copy the daily options-watchlist post and re-publish it to our trade-alert Discord channel.
scope: read + repost read: signal-source-discord post: existing alert webhook status: PROPOSAL date: 2026-06-03

1 · Goal

Each trading morning, TradingTheTrend posts an options "watchlist" — conditional breakout/breakdown levels — in the source channel 769790224921395200 / 769797819770732554. We want it automatically mirrored into our existing trade-alert Discord channel (the same place order-failure and signal-feed alerts already go), cleanly, once per day.

Read-then-repost only. No trades; independent of the copytrade signal path.

2 · Locked decisions

Q1
Posting mechanism: reuse the existing trade-alert webhook (ALERT_DISCORD_WEBHOOK_URL, secret discord-alert-credentials) — the same channel/transport trade alerts already use. No new webhook.
Q2
Source: the watchlist lives in a different channel than the copytrade signal channel → a dedicated DISCORD_WATCHLIST_CHANNEL_URL + a second reader.
Q3
v1 fidelity: raw-faithful passthrough — mirror the text as posted; no watchlist parser in v1.
Q4
Timing: post on detection (no held/scheduled send).
Q5
Bridge (§6): Option B — sidecar emits a tiny Temporal workflow → orchestrator activity reuses the existing WebhookClient.post(). Truly the same mechanism; webhook secret stays in the Java services; durable delivery.

3 · What already exists

CapabilityToday
Read any channelhave The Python sidecar signal-source-discord scrapes a Discord channel via Playwright (extract_recent()), polling one channel (DISCORD_CHANNEL_URL) ~1s.
Outbound alert → Discordhave The Java services post alerts via DiscordWebhookClient.post(content) → {"content": ...} to ALERT_DISCORD_WEBHOOK_URL. Used by OrderFailureAlerter, SignalFeedAlerter (orchestrator) & BrokerRejectionAlerter (exec). Best-effort, non-blocking, no-op when URL blank.
Feed-mirror precedenthave SignalFeedAlerter already mirrors "what the sidecar saw" into the alert channel — but it fires off audit events from trading workflows, which a watchlist is not.
Sidecar → Java transporthave The sidecar emitter.py starts Temporal workflows (CopytradeSignalWorkflow). This is the only existing channel from sidecar into the Java side.
Sidecar outbound HTTPmissing The sidecar is read-only — no HTTP client, no webhook code.
Watch a 2nd channelmissing The watcher is hard-wired to one channel URL.

The crux: the watchlist is read by the Python sidecar, but the alert mechanism lives in Java. Bridging that gap is the one open design choice — see §6.

4 · The watchlist format

Today's post (verbatim). Note it is not the BTO/STC grammar the bot parses — so v1 doesn't try to:

TradingTheTrend — 8:19 AM
SPY         762c      >       761.00
                  753p     <      754.00

SHOP       121c        >     120.00

ORCL        250c      >     247.00

UNH         385c        >     381.00

TSM          455c        >     450.00

TSLA         430c        >      425.00
                    410p        <       413.00
  • Ticker blocks; continuation lines omit the ticker (753p→SPY, 410p→TSLA).
  • > = call if underlying trades above the level; < = put if below. Watch levels, not orders.
  • Irregular whitespace. v1 passthrough preserves it; v2 (later) could parse + prettify with a raw fallback.

5 · Proposed flow

Discord "options-watchlist" channel (source — read only) │ Playwright scrape (reuse extract_recent) ▼ WatchlistWatcher (NEW, in the sidecar) — slow poll ~45s of DISCORD_WATCHLIST_CHANNEL_URL │ detect: author == TradingTheTrend AND watchlist-shaped AND not already mirrored today │ ▼ ── bridge to the Java alert mechanism (see §6 — the one open choice) ── │ ▼ DiscordWebhookClient.post(formatted) ──HTTPS──> ALERT_DISCORD_WEBHOOK_URL (our trade-alert channel) │ └─ record "mirrored YYYY-MM-DD (ET)" to durable PVC state → post once/day, survives restarts

6 · The one open choice — how the sidecar reaches the alert webhook

"Use the same mechanism as trade alerts" can mean two things. They differ on where the webhook secret lives and how much plumbing we add. I recommend Option B.

RECOMMENDED — Option B Route through the Java alerter

Sidecar detects the watchlist → emits a tiny Temporal workflow (like it already emits signals) carrying the raw text → a new orchestrator activity calls the existing WebhookClient.post().

  • + Literally the same mechanism — reuses DiscordWebhookClient (DRY); mirrors the SignalFeedAlerter pattern.
  • + Webhook secret stays in the Java services only — never enters the browser-automation pod (better hygiene).
  • + Durable delivery + retry for free via Temporal; a sidecar restart mid-send is covered.
  • − More plumbing: 1 contract payload + 1 small workflow + 1 activity (all established patterns here).
LIGHTER — Option A Post from the sidecar directly

Add httpx to the sidecar; POST the same {"content": ...} straight to ALERT_DISCORD_WEBHOOK_URL.

  • + Smallest code (~1 file); no Java/contract/workflow changes.
  • − Re-implements the webhook transport → a second mechanism, not "the same" one.
  • − Moves the alert-webhook secret into the sidecar pod (the larger attack surface).
  • − No durable retry; best-effort only.

Both honour Q1 (same destination webhook), Q4 (post on detection), and need no change to the trading path.

7 · Components to build

Shared (both options)

  • config — sidecar env: DISCORD_WATCHLIST_CHANNEL_URL, WATCHLIST_AUTHOR (default TradingTheTrend), WATCHLIST_POLL_INTERVAL_SECS (default 45), WATCHLIST_MIRROR_ENABLED (default false → opt-in).
  • watchlist detector (sidecar) — author gate + loose shape heuristic (≥2 lines of TICKER … >/< price) so chit-chat isn't mirrored.
  • WatchlistWatcher (sidecar) — second slow poller reusing extract_recent; runs concurrently with the signal watcher via asyncio.gather behind the enable flag; heartbeat preserved. Reuses the existing Discord token — the auth is a portable user-account session in storage_state.json (not server-scoped), so it opens the watchlist channel with no second login/token, provided the account is a member of that channel's server. Prod server 769790224921395200: already a member (it ingests TradingTheTrend's signals there). Dev server 878725319178207302: confirm the account is invited.
  • durable state — "last mirrored date / message_id" on the existing /app/state PVC → once/day, restart-safe.
  • formatter — wrap the raw text in a fenced block with a header ("📋 Watchlist — Jun 3, 2026 — via TradingTheTrend").

Option B adds

  • contract — a small WatchlistMirror payload schema (date, author, raw_text, source message_id).
  • sidecar emitter — start a WatchlistMirrorWorkflow (id keyed on the source message_id → Temporal dedupe).
  • orchestrator — WatchlistMirrorWorkflow (one step) → postWatchlistAlert activity → existing WebhookClient.post(formatted). No new schema ownership, no DB.

Option A adds

  • sidecar publisher — add httpx; AlertPublisher.post() → ALERT_DISCORD_WEBHOOK_URL; mount that secret into the sidecar.

Guardrail (repo CLAUDE.md): keep to the above — no speculative multi-author/multi-channel/scheduler. Signal path untouched.

9 · Build sequence

  1. Detector + state + formatter (sidecar) — author/shape classification, durable "mirrored today", header format. verify: chit-chat vs. watchlist classified right; restart doesn't re-post.
  2. WatchlistWatcher wired behind WATCHLIST_MIRROR_ENABLED, concurrent with the signal watcher. verify: signal path unchanged; heartbeat green.
  3. Bridge — Option B: contract payload + WatchlistMirrorWorkflow + postWatchlistAlert activity reusing WebhookClient; Option A: httpx publisher to the webhook. verify: today's sample → exactly one message in the alert channel.
  4. Infra — secret/template key, deployment env, compose; spotless:apply for any Java (Option B). verify: kubeconform + manual homelab apply.
  5. v2 fast-follow — tolerant watchlist parser → prettified embed with guaranteed raw fallback + tests.

10 · End-to-end verification

  • Post the sample as TradingTheTrend in a test source channel → within one poll, exactly one clean mirror appears in the trade-alert channel.
  • Post again / restart the pod → no duplicate that day.
  • Non-watchlist chatter from the same author → not mirrored.
  • Copytrade signal flow (BTO/STC → Temporal) unchanged with the flag off, unaffected with it on.
  • Webhook URL never logged or committed; lives only in the operator secret.
